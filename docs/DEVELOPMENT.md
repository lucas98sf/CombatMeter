# Local development and debugging

Development uses .NET SDK **10.0.401** under `.tools/dotnet`. The `.tools`, `.cache`, and `.profiles` directories are ignored by Git: a fresh checkout or a source-only move needs bootstrap and profile setup again. No system-wide SDK is required. `global.json` selects the workspace SDK version and searches `.tools/dotnet` before the running host's installation. This SDK search-path feature requires a .NET 10 or newer host. Plugins target net6.0 for BepInEx; tests run on net10.0. The SDK, game runtime, and C# language version are separate settings.

Open PowerShell in the repository and enable this session's script execution:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
# First checkout, or if the local SDK / build references are missing:
./scripts/bootstrap.ps1
./scripts/setup-profile.ps1
. ./scripts/enter-dev.ps1
dotnet --list-sdks
./scripts/build.ps1 -Configuration Debug
```

The development shell prepends the local SDK to PATH without changing the system environment. Build scripts also invoke it explicitly, so they work without changing PATH. Debug builds generate matching portable PDBs alongside the DLLs and disable normal Release optimizations.

## Test through your Thunderstore profile

Prepare hot reload once, after closing the game normally and allowing its local server to finish saving:

```powershell
./scripts/build.ps1 -Configuration Debug
./scripts/enable-hot-reload.ps1 -Configuration Debug
```

This installs Debug DLLs and matching PDBs into the Default profile, with backups and checksum checks. Use `-ProfilePath` for another profile. It keeps Runtime, Core, and Shared in the ordinary plugins folder and moves Client/Server into a Bloodpebble reload folder. Both client and bundled-server Bloodpebble configs watch the same absolute directory, with automatic reload enabled and a two-second delay. Existing tracking preferences are preserved.

If the game is running, use `./scripts/queue-thunderstore-update.ps1 -HotReloadSetup -Configuration Debug`. Exit the game within 20 minutes, then wait for `Development profile configured` in the printed installation log before relaunching. A queue timeout makes no installation changes; queue it again or run setup with the game closed. The watcher needs the receipt generated by successful setup.

Start **Modded** through Thunderstore once after preparation, then open your private game. ServerLaunchFix starts its server using the shared plugin directory. During development, run:

```powershell
./scripts/reload-dev.ps1 -Mode Client -Watch
```

Save changes under `src/CombatMeter.Client`: the script rebuilds with the local SDK, publishes matching symbols and the DLL, and Bloodpebble reloads the HUD. Ctrl+C stops the watcher. Use `-Mode Server` for collector changes or `-Mode Both` to publish both plugins; omit `-Watch` for a single build/deployment. VS Code includes client build/reload and watch tasks.

Client reload requests fresh snapshots and history from the running server. Server reload starts a new meter session and clears encounter history, then asks connected clients to register again. Unloading releases callbacks, packet handlers, ECS queries, UI objects, and input contexts. Build failures leave the running plugin in place.

Runtime holds permanent native detours, Harmony hooks, and the injected Unity behaviour. Changes to Runtime, Core, or Shared require closing the game, rerunning `enable-hot-reload.ps1`, and restarting once. The reload script checks these DLL hashes and refuses deployment if they changed. After preparing this profile, use `reload-dev.ps1` for routine changes; the ordinary installer would put Client/Server back in the permanent folder.

Server automatic unload/reload was verified twice in one isolated process; native damage still routed after reload. Client HUD unload/reload needs an interactive check in your next session. Bloodpebble does not remove all IL2CPP/native lifetime restrictions.

For the isolated development profiles instead:

```powershell
./scripts/deploy-profile.ps1 -Configuration Debug
./scripts/start-profile.ps1 -Mode server
./scripts/start-profile.ps1 -Mode client
```

Connect the isolated client to 127.0.0.1:29878. The client script requires other V Rising clients to be closed.

## Breakpoints

Install the Microsoft C# extension in VS Code and open `CombatMeter.sln`. C# Dev Kit can resolve the local SDK through the search paths in `global.json`. If it previously reported "A compatible .NET SDK was not found", run **Developer: Reload Window** from the Command Palette to retry project initialization. For tools using an older .NET host, start VS Code from the development shell with `code .` so its tools inherit the SDK path; close existing VS Code instances first. The workspace includes a Debug build task and CoreCLR attach configurations.

Launch the game first. Use Run and Debug, select the server or client attach entry, and choose the corresponding `VRisingServer.exe` or `VRising.exe` PID. Debug symbols must belong to the exact installed DLL. This attaches to managed CombatMeter/BepInEx code; game IL2CPP/Burst native code needs different tooling. Debugger attachment to this game's embedded runtime has not yet been validated. The `UnityMono.debug_enabled` Doorstop option does not enable debugging of this IL2CPP/CoreCLR plugin.

Useful first breakpoints: server `BeforeHealth`, `AfterHealth`, and transport `Register`; client `OnPolicy`, `OnEncounter`, and transport `PollConnection`. Pausing the server for too long can disconnect the client.

See [Microsoft's C# process-attach instructions](https://code.visualstudio.com/docs/csharp/debugging#_attaching-to-a-process).

## Logs and diagnosis

Version 0.1.6 adds source breakdowns and changes Core/Shared to protocol 3. Stop any running watcher, close the game, rerun the hot-reload setup (or queue it), and restart through Thunderstore once. Start a new watcher afterward so it reads the refreshed stable-library hashes. With resolved-damage diagnostics enabled, `[CombatMeter:DamageSource]` logs the resolved source ID/name and its measured damage. Check actual casts against these lines; synthetic prefab probes do not validate the game's event relationship for every attack.

Your Thunderstore profile is `%APPDATA%/Thunderstore Mod Manager/DataFolder/VRising/profiles/Default`. Client log: `BepInEx/LogOutput.log`. Local server log: `BepInEx_Server/LogOutput.log`. Isolated profiles use `.profiles/{client,server}/BepInEx/LogOutput.log`.

With server `Diagnostics.LogResolvedDamage=true`, inspect:

- Native game connection and CombatMeter registration/policy receipt: confirm the UI connection exists.
- `healthHookCalls`: confirm native resolved-health interception executes.
- `captured`: confirm negative health operations were measurable.
- `routed` and `active`: confirm enabled modes and attribution route events to encounters.
- `subscribers`: confirm registered clients are receiving totals.

Before/after health logs show the measured amount and native change value. Compare them with actual health readings for direct hits, mitigated hits, shields, DoTs, overkill, and simultaneous attackers. Turn verbose diagnostics off after verification. Debug compilation does not itself prove that a native Harmony hook is called.

## Built-in networking in 0.2.0

Protocol 4 removes Emberglass. Requests travel as private self-directed native messages, and the server sends directed system-message frames only to registered users. Runtime hooks consume the reserved channel before normal chat routing/display. There is no chat CLI or additional network port. Connected FromCharacter.User provides server-side requester identity. Brotli/JSON packets have bounded frame counts, decompression limits, transfer expiry, direction checks, duplicate rejection, and a fresh client channel per connection.

Rebuild both configurations, close the game, and rerun scripts/enable-hot-reload.ps1 once: Runtime/Core/Shared changed. Existing Emberglass installs are left alone in case another mod needs them. For dependency-free validation, disable Emberglass in the test profile before starting it. The local-game client/server round trip, encounter delivery, source replies, and client hot reload were verified during 0.1.7 development. Readiness queries the actual LocalUser entity rather than a fixed world name or the server-side User.IsConnected flag. Broader multiplayer, reconnect, and normal-chat checks remain in the validation record.
